# Архитектура LAVRay для Android (контракт для разработки)

## Раскладка репозитория

```
third_party/lavray/        субмодуль, тег v0.9.3 (только чтение)
core-overlay/              Go-код, копируется в build/go/core/mobile при сборке
scripts/build-core.sh      собирает app/libs/lavray-core.aar
tools/                     генераторы (DTO из proto, словари, иконки)
app/                       Android-приложение (Kotlin, Compose)
docs/                      записки, замеры, чек-листы
```

Идентификатор приложения: `io.github.anatolijlaptev1991_ctrl.lavray` (как у десктопа, дефис заменён: в Android он недопустим).
minSdk 26, targetSdk и compileSdk 36. ABI: arm64-v8a, armeabi-v7a, x86_64. Версия приложения 0.9.4, ядро v0.9.3. `versionCode` каждого APK = базовый номер × 10 + номер ABI (armeabi-v7a 1, arm64-v8a 2, x86_64 3), чтобы 32-битный APK не встал поверх 64-битного (`app/build.gradle.kts`, проверка в `scripts/ci-apk.sh verify`). Перед подписью релиза APK пережимается 7-Zip (`scripts/ci-apk.sh recompress`).

## Контракт Go ↔ Kotlin (пакет gomobile `mobile`, Java-пакет `lavray.core.mobile`: классы `Mobile`, `Options`, `Platform`, `NetworkListener`; библиотека `libgojni.so`)

Сложные структуры передаются строкой JSON: это избавляет от итераторов gomobile.

```go
package mobile

// Platform реализует Kotlin (процесс :vpn).
type Platform interface {
    // OpenTun вызывает VpnService.Builder.establish и возвращает дескриптор.
    // optionsJSON: {mtu, inet4:[cidr], inet6:[cidr], dns:[ip], includePackages:[], excludePackages:[],
    //   route4:[cidr], route6:[cidr]} (route* считает sing-box; без них добавьте 0.0.0.0/0 и ::/0).
    // Kotlin возвращает НЕЗАВИСИМЫЙ дескриптор (dup + detach): им владеет Go и закрывает его вместе с туннелем;
    // исходный держит Kotlin (TunHolder), пока интерфейс должен существовать.
    OpenTun(optionsJSON string) (int32, error)
    // Protect вызывает VpnService.protect(fd).
    Protect(fd int32) error
    // FindOwnerUid вызывает ConnectivityManager.getConnectionOwnerUid (API 29+), -1 если нет.
    FindOwnerUid(proto int32, srcIP string, srcPort int32, dstIP string, dstPort int32) (int32, error)
    PackagesForUid(uid int32) string // пакеты через запятую
    // Монитор сети по умолчанию; listener вызывается при каждой смене.
    StartNetworkMonitor(l NetworkListener) error
    CloseNetworkMonitor() error
    // Interfaces возвращает JSON-массив {name,index,mtu,addrs:[cidr],flags,metered,type};
    // flags — маска IFF_* Linux из OsConstants по транспорту (Wi-Fi и Ethernet: UP|RUNNING|BROADCAST|MULTICAST, сотовая: UP|RUNNING|POINTOPOINT|MULTICAST; нет поля: UP|RUNNING|MULTICAST), dns и gateway — адреса из LinkProperties, type — "wifi"|"cellular"|"ethernet"|"other",
    // необязательные dns:[ip] и gateway:[ip] попадают в Environment() локального DNS.
    Interfaces() (string, error)
}

type NetworkListener interface {
    // name "" и index -1 означают отсутствие сети.
    Update(name string, index int32, metered bool)
}

type Options struct {
    DataDir, TempDir, SocketPath, AuthToken string
    MemoryLimitMB int32 // 0 — без ограничения (debug.SetMemoryLimit)
    TimeZone      string // IANA, java.util.TimeZone.getDefault().id; у Go на Android нет /etc/localtime
}

func Start(o *Options, p Platform) error // синхронно: возвращается, когда API готов
func Stop()                              // корректное завершение, идемпотентно
func Version() string
func SetTun(stack string, mtu int32) // MTU со следующего подключения; stack не действует, на Android всегда gvisor
```

Не ожидайте от `Start` режима «системный прокси»: ядро запускается только с tun-inbound (подключение `CONNECT_MODE_TUN`), иначе Connect вернёт ошибку.

Подмешивание платформы: HTTP-обёртка с `service.ContextWith` не годится. Значения контекста переживают `context.WithoutCancel`, но `ContextWith` кладёт в контекст общий изменяемый реестр служб sing-box; временные инстансы проверки задержки наследуют контекст одного RPC и работают параллельно, так что делили бы и затирали Router, журнал и NetworkManager друг друга. Поэтому каждый экземпляр (рабочий и временный) получает контекст с НОВЫМ реестром, платформой и реестром DNS-транспортов, где `local` заменён системным резолвером Android. Рабочий раннер делает это в `Start`, временные инстансы получают фабрику `api.Server.newTestInst` (устанавливается при `Mobile.start`). Один слушатель сети Kotlin обслуживает все экземпляры (хаб).

Обёртка раннера над `inst.SingBoxRunner` приводит конфиг к правилам Android перед стартом:
- удаляется `mixed-in` и любой слушатель на localhost: другие приложения на телефоне не должны видеть локальный прокси;
- из правил убираются условия `process_name` и `process_path` (на телефоне они ничего не выбирают, а поиск владельца соединения стоит вызова Binder);
- у `tun-in` убирается `interface_name`, `stack` всегда `gvisor` (стеки `system` и `mixed` не передают данные, пока приложение исключено из своего VPN: ответы TCP-слушателя ядра уходят мимо tun0), `mtu` берётся из `Mobile.setTun`;
- также убираются `experimental.clash_api` и `experimental.v2ray_api` (локальные слушатели), `route.default_interface` и `route.default_mark`; `auto_detect_interface` остаётся: при платформе он включает `Protect(fd)` на каждый исходящий сокет, а к интерфейсу не привязывает;
- правило, оставшееся без условий после снятия `process_*`, удаляется;
- поиск владельца соединения (`FindOwnerUid`) выполняется, только если в конфиге есть `package_name`, `user`, `user_id` или `find_process`; иначе Binder не вызывается.

## Процессы и запуск

`LavrayVpnService : VpnService` в процессе `:vpn`, FGS-тип `specialUse` (документация не запрещает его запуск из `BOOT_COMPLETED`; `systemExempted` бросает исключение, если согласия на VPN нет).

`onBind`: для `VpnService.SERVICE_INTERFACE` — `super.onBind`, иначе собственный `Binder` с `endpoint()` (путь сокета и токен).

Ядро Go стартует лениво при первом `onBind` или `onStartCommand`. Интерфейс привязывается к службе после первого нарисованного кадра (`MainActivity.bindAfterFirstFrame`): запуск процесса `:vpn` с библиотекой ядра на 2 vCPU отнимал у первого кадра около 10% времени холодного старта. Когда VPN выключен и интерфейс отвязался, сервис вызывает `Mobile.stop()` и завершает процесс, чтобы вернуть память рантайма Go.

Своё приложение исключается из туннеля (`addDisallowedApplication(packageName)`), поэтому сокеты ядра и временные инстансы проверки не попадают в петлю. В режиме белого списка приложений это выполняется автоматически.

Дескриптор TUN: Kotlin держит `ParcelFileDescriptor` (`TunHolder`), ядру отдаёт независимую копию (`dup().detachFd()`), которой владеет Go. У каждого интерфейса есть поколение: закрытие, решённое против старого поколения (`releaseIfCurrent`), игнорируется, так что запоздавшее событие прошлого запуска не закроет новый интерфейс. Kotlin закрывает свой дескриптор, когда ядро перестало быть активным и держать интерфейс незачем (правило ниже), при неудачной попытке, при отключении и в `onDestroy`: без этого интерфейс с маршрутом `0.0.0.0/0` переживал бы отключение и блэкхолил трафик устройства.

Монитор сети: `registerDefaultNetworkCallback` после установки туннеля сообщает сам туннель как сеть по умолчанию, поэтому физическую сеть наблюдает запрос без VPN (`registerBestMatchingNetworkCallback` на API 31+, `requestNetwork` на 26-30: перегрузка с `Handler` есть с API 26 и требует только `CHANGE_NETWORK_STATE`, документация на developer.android.com ограничений для 26-27 не называет).

Запросы ядра «через туннель» без слушателя: `core-overlay/patches/0001-tunnel-in-process-dial.patch` (применяет `scripts/build-core.sh` к копии `build/go`, при неудаче сборка падает) заменяет `tunnelClient` на `http.Client`, транспорт которого вызывает `inst.Manager.DialProxy` внутри процесса (`core-overlay/inject/api/tunnel_inproc.go`). Имя хоста уходит серверу профиля, сокета на localhost нет, прокси из окружения не читается. Так работают публичный IP через туннель, самопроверка, проверка часов, утечки и подписки с `sub.use_proxy=true`.
- `tunnelIsTUN` на Android всегда «да»: ядро запускается только с tun-inbound, поэтому проверка маршрута строится по TUN-конфигу и до подключения.
- Своё приложение исключено из VPN, поэтому «прямой» замер ядра (публичный IP напрямую, отчёт утечек) идёт по физической сети и достоверен: `directIsTunneled` = false.
- «Прямой IPv6» из процесса не измеряется (`ipv6Measurable` = false): исключённый процесс видит IPv6 всегда, где он есть у телефона. Отчёт называет замер непроведённым, а не «в порядке».
- Проверка «порт свободен» не применима (`hasLocalListener` = false). Скачивание обновления через туннель не используется: самообновление не перенесено.
- Значение `sub.use_proxy=false` по умолчанию (`core-overlay/defaults.go`) осталось: подписка берётся напрямую, потому что приложение вне туннеля.

## Приложения в туннеле

Выбор «все / только выбранные / все, кроме выбранных» хранит процесс `:vpn` (`VpnPrefs.appSelection`, JSON `{"mode","packages"}`), интерфейс читает и пишет его через AIDL `getAppSelection` и `setAppSelection`. `TunEstablisher` подмешивает выбор к параметрам TUN ядра (`AppSelection.applyTo`) при каждом построении туннеля; «только выбранные» с пустым списком считается «все» (иначе `Builder` не получил бы разрешённых приложений). Изменение действует со следующего построения туннеля: интерфейс отмечает его как «сохранено, но ещё не в туннеле» (`PendingReason.Apps`) и предлагает «Переподключить сейчас» (`Reconnect.now`, то есть `reconnect(0)`). Список приложений: `<queries>` с интентом MAIN и LAUNCHER, без `QUERY_ALL_PACKAGES`.

## Автоподключение

- `BootReceiver` в процессе `:vpn`: `BOOT_COMPLETED`, `QUICKBOOT_POWERON` (AOSP и HTC). `UpdateReceiver` там же: `MY_PACKAGE_REPLACED` (обновление убивает туннель, а `BOOT_COMPLETED` не приходит). Оба не экспортируются. Настройка «Подключаться при запуске телефона» хранится в SharedPreferences процесса `:vpn`; все записи через `commit()`.
- Загрузка: туннель поднимается, если включено автоподключение. Обновление: если туннель был нужен (`wantConnected` той же загрузки: после перезагрузки желание прочитывается как сброшенное), независимо от автоподключения. Согласия нет: уведомление и `needsPermission` в сохранённом состоянии. `startForegroundService` в приёмнике защищён: отказ системы даёт уведомление и `lastFailure`, не падение.
- Приёмник загрузки включён по умолчанию в манифесте и выключается, пока автоподключение выключено (`PackageManager.setComponentEnabledSetting`, `DONT_KILL_APP`), чтобы процесс `:vpn` не создавался при каждой загрузке впустую. Включение — возврат к значению по умолчанию. Состояние приводится в соответствие с настройкой при записи настройки, при каждом создании службы, в самом приёмнике загрузки и в `UpdateReceiver` (установка поверх старой версии начинается с включённым приёмником). Отказ системы при выключении оставляет приёмник включённым, при включении повторяется при следующей сверке; «автоподключение молча выключено» невозможно из-за одной неудачи.
- `VpnService.prepare() != null`: согласие утеряно. Сервис не стартует, показывается уведомление «Нужно разрешение VPN». Вызовы из Receiver документацией не описаны, поведение проверяется на эмуляторе.
- Запуск без нашего extra считается запуском системы (Always-on), такой запуск тоже подключает последний сервер.
- Манифест не отключает `SUPPORTS_ALWAYS_ON`.
- Ожидание сети: `NetworkCallback` по `NET_CAPABILITY_INTERNET` и `NOT_VPN`. Без опроса, без WakeLock и без AlarmManager.
- Повторы после сбоя: 5 с, 15 с, 45 с, 2 мин, далее 5 мин с разбросом ±20%; появление сети сбрасывает задержку; ручное «Отключить» отменяет всё.

## Мост без дыры: удержание интерфейса при переходах

Закрытие интерфейса на время пересборки отдало бы весь трафик физической сети. Поэтому Kotlin держит интерфейс как блэкхол (его никто не читает, пакеты пропадают), пока выполнены ВСЕ условия (`BlackholePolicy`, `LinkWatch`):

1. интерфейс удерживается Kotlin, и его никто не читает: ядро не работает (нет CONNECTING, CONNECTED, DISCONNECTING, RECONNECTING) либо работает, но ещё не заменило интерфейс новым (оно в CONNECTING до вызова `OpenTun`). Удержание, которое уже началось, одним лишь «ядро активно» не снимается и продолжает считаться до предела; его снимает только новый интерфейс (поколение больше, чем при начале удержания);
2. туннель был установлен (ядро хотя бы раз дошло до CONNECTED в этой сессии) и его не останавливали намеренно;
3. разрыв вызвало само приложение: льготный период после падения или перезапуска ядра (12 с; отменяется следующим CONNECTING или CONNECTED), либо идёт попытка подключения (переподключение, смена сервера, повтор сразу после потери);
4. с начала удержания прошло меньше 30 с. Предел настоящий: `blackholeUntilMs` в статусе честно показывает, что трафик заблокирован, пока удержание длится, в том числе пока ядро сидит в CONNECTING.

Удержание не применяется, пока служба ждёт сеть (`WAITING_NETWORK`), в паузе между повторами (`BACKING_OFF`), после окончательной ошибки, при ручном «Отключить», при отзыве согласия и для первой попытки, которая ещё ни разу не подключилась: приложения сразу получают обычное подключение. Удержание заканчивается, когда новый `establish()` заменил интерфейс, либо по жёсткому пределу 30 с: тогда интерфейс закрывается, в сохранённое состояние пишется `lastFailure` с `failureKind = protection_off` и показывается уведомление «Защита выключена». Пока интерфейс удержан, в статусе `blackholeUntilMs` больше нуля. Служба остаётся в переднем плане всё время перехода.

Ядро идёт через IDLE при собственном перезапуске (`RestartProfile`): CONNECTED, DISCONNECTING, IDLE, CONNECTING, CONNECTED. Падение установленного туннеля поэтому сначала льготный период, а не потеря; потеря объявляется, только если ядро не вернулось за 12 с. Для смены сервера интерфейс должен вызывать `reconnect(profileId)` (AIDL, `VpnController.reconnect`), а не `disconnect()` с последующим `connect()`: второе — осознанное отключение, и приложения получают прямое подключение.

Важно: только системный Always-on с «Блокировать подключения без VPN» остаётся закрытым при гибели процесса и при отключении пользователем; блэкхол приложения этого не заменяет.

## Устойчивость службы

- `START_STICKY`. «Туннель нужен» (`wantConnected`, `commit()`) пишут только точки входа, несущие намерение: нажатие пользователя (`connect`/`reconnect` в Binder, до запуска службы), приёмники загрузки и обновления, Always-on системы (`StartSource.SYSTEM`) и перезапуск системой. Исполнение уже записанного запроса и результат подключения желание не пишут. Сбрасывает его ручное отключение (в Binder и в цикле), отзыв согласия, окончательная ошибка и всякая самостоятельная остановка службы (без записи ошибки). Перезапуск системой (null-интент, `StartCommand.Resume`) подключает, только если `wantConnected`, согласие есть и процесс не падал подряд до первого CONNECTED (`ResumePolicy`: после 3 перезапусков без CONNECTED служба останавливается с `failureKind = repeated_crash`, а не крутит цикл падений). Счётчик перезапусков обнуляется не по CONNECTED, а когда туннель продержался CONNECTED 3 минуты (`SessionEngine.STABLE_MS`): падение ядра через несколько секунд после CONNECTED всё равно считается.
- Порядок команд: каждая команда пользователя получает номер (`userSeq`). Команда, которую обогнала более новая из ещё не разобранных, считается устаревшей и отбрасывается (подключение, смена сервера и отключение). Поэтому ни результат попытки, ни запоздавший `Connect` не отменяют отключение, а очередь `[Connect, Disconnect, Connect]` заканчивается подключением. Пока в очереди есть команда пользователя, служба не останавливается и не уходит из переднего плана.
- Желание, `unexpectedStop`, `stopReason` и счётчик перезапусков относятся к одной загрузке телефона: они хранятся вместе с `Settings.Global.BOOT_COUNT` и после перезагрузки читаются как сброшенные. Через перезагрузку намерение переносит только настройка автоподключения. Номер загрузки берётся из `BOOT_COUNT`; рядом хранится идентификатор загрузки ядра (`/proc/sys/kernel/random/boot_id`), он отличает загрузки на прошивках, где счётчик не растёт (быстрая загрузка) или отсутствует. Нечитаемый идентификатор ничего не сбрасывает.
- Запись `ApplicationExitInfo` (API 30+) только подписывает остановку для интерфейса (`stopReason`), решения службы от неё не зависят. Она не отличает принудительную остановку от смахивания из «Недавних», от чистильщика прошивки и, до API 34, от обновления: `REASON_USER_REQUESTED` (10) значит и то, и другое, а обновление получило свой код `REASON_PACKAGE_UPDATED` (16) и `REASON_PACKAGE_STATE_CHANGE` (15) только с API 34. Вывод «пользователь хотел выключить» по такой записи оставил бы телефон без защиты молча, а ошибочное «умер» стоит лишь баннера, поэтому желание не сбрасывается: перезапуск системой и обновление восстанавливают туннель, а после настоящей принудительной остановки (перезапуска нет) пользователь видит баннер с `stopReason = user_requested` (формулировка для интерфейса нейтральная: «закрыто вами или системой»). Берётся только запись самого свежего завершения процесса `:vpn` этой загрузки (имя процесса точное, старые записи отбрасываются).
- `wantConnected = true` в только что созданном процессе той же загрузки означает, что прошлый процесс умер без чьего-либо решения: пишется `unexpectedStop` с причиной из `ApplicationExitInfo` (API 30+: `low_memory`, `crash_native`, `user_stopped` и т. д.; читается только тогда) или `process_died`. Сбрасывается при следующем успешном подключении и при ручном отключении.
- Попытка подключения считается успешной только по CONNECTED (ожидание потока событий ядра в пределах 90 с). ERROR до первого CONNECTED означает неудачу попытки (повтор или ошибка), а не «подключено». Один и тот же профиль в полёте не отменяется повторным запуском (`AttemptGate`); результаты устаревших попыток (поколение) отбрасываются.
- Ручное «Отключить» никогда не заканчивается показанной ошибкой (при остановке статус не показывает ERROR ядра). Ожидание ответа ядра на `Disconnect` ограничено 15 с; затем ядро останавливается снизу (`Mobile.stop()` на отдельном потоке, тоже с пределом 15 с, цикл событий не замерзает), токен API становится недействительным, `coreEpoch` в статусе растёт: интерфейс заново берёт `endpoint()` (`CoreSession.onCoreEpoch`; клиент ядра в интерфейсе и без того сбрасывается при отказе токена). Если и остановка не уложилась, пишется `failureKind = core_stop_timeout`, показывается уведомление и процесс `:vpn` завершается: зависшее ядро Go держит замок ядра навсегда, и никакой следующий запуск в этом процессе не удался бы. Пока действует busy-удержание, процесс не завершается (идущее восстановление не приносится в жертву догадке), завершение откладывается до его конца. Желание в момент остановки сброшено, но Connect, записанный за время зависания, переживёт процесс: новый процесс подхватит его перезапуском системой (`Resume`). Интерфейс переподключается к новому процессу. Тот же предел 15 с стоит и на остановке ядра в `onDestroy`: по его истечении процесс завершается, иначе ядро следующего экземпляра службы в этом же процессе ждало бы зависшее.
- Поток событий ядра держится открытым (`CoreWatcher`): если он оборвался, пока ядро в работе, он открывается заново с паузой 2 с и состояние берётся вызовом статуса, иначе служба осталась бы с «подключено» на мёртвом туннеле и не запустила бы льготный период. Если поток обрывается сразу и каждый раз, пауза растёт с 2 до 30 секунд; любое событие возвращает 2 секунды.
- Цикл событий не падает от одного сбоя (ловится `Throwable`, кроме отмены), и каждый эффект движка исполняется, даже если предыдущий упал; `VpnBinder.broadcast` и доставка нового наблюдателя синхронизированы одним замком, так что устаревший статус не обгонит новый; `LinkageError` при загрузке ядра превращается в «ядро не запустилось» (`CoreStartException`).
- Решения службы вынесены в `SessionEngine` (события на входе, эффекты на выходе, без типов Android), служба только исполняет эффекты; порядок событий, перезапуск, отказ системы и поколения интерфейса проверяются на JVM.
- Отказ системы в переднем плане после принятого `startForegroundService` (запуск службы, который обещал `startForeground`) учтён и не лечится настройкой: манифест уже объявляет тип `specialUse`, разрешение `FOREGROUND_SERVICE_SPECIAL_USE` и свойство подтипа, а отказ внутри `startForeground` следует за решением системы об ограничении фонового запуска, которого приложение не контролирует. Служба тогда записывает сбой, показывает уведомление и завершает started-состояние (`StopSelf`, если туннель не работает); если система всё же засчитает невыполненное обещание падением, умирает только `:vpn`, желание сброшено сбоем, а перезапуск системой (запуск без `startForegroundService`) обещания не даёт.
- Один владелец Go-ядра на процесс (`CoreLifecycle`): запоздавший `stop` старой службы не останавливает ядро новой, а новая служба сначала останавливает прежнее ядро.
- Выбранный пакет, которого нет, пропускается и попадает в `skippedPackages`; ошибка только если «Только выбранные» не нашли ни одного установленного приложения (`failureKind = apps_none`, постоянная ошибка без повторов).
- IPv6 выключен: IPv6 приложений в туннеле заблокирован (`allowFamily` не вызывается), напрямую не уходит. Ядро ставит у DNS стратегию `ipv4_only` (`core-overlay/patch_ipv6.go`), чтобы приложения не ждали ответ AAAA. У sing-box пустая стратегия резолвера наследует `dns.strategy` (`dns/router.go`), поэтому каждый резолвер доменов серверов без своей стратегии (`default_domain_resolver`, `domain_resolver` у outbound, endpoint и DNS-серверов) получает `prefer_ipv4`, и сервер только с IPv6 остаётся доступен. Уже заданная `dns.strategy` не перезаписывается; без `route.default_domain_resolver` правка не делается вовсе.

## Статус службы для интерфейса

Интерфейс получает статус через `IVpnObserver.onStatus(state, error, detail)`: `state` — код `VpnState`, `error` — текст только при ERROR, `detail` — JSON с остальными полями (`VpnStatusWire`; нет ключа — значение по умолчанию, лишние ключи игнорируются). В Kotlin это `VpnStatus` (`VpnController.status`). Статус приходит сразу при регистрации и при каждом изменении.

| Поле | Тип | Смысл |
|---|---|---|
| `state` | `VpnState` | IDLE, CONNECTING, CONNECTED, DISCONNECTING, WAITING_NETWORK, NEEDS_PERMISSION, ERROR. Льготный период после падения ядра и пересборка показываются как CONNECTING. После ручного отключения ERROR не показывается. |
| `error` | `String?` | Короткий текст, только при ERROR. |
| `healthError` | `String?` | `CoreStatus.health_error` ядра: код, непустой только при `state == CONNECTED`. Значит «подключено, но через сервер ничего не проходит». |
| `unexpectedStop` | `Boolean` | Туннель был нужен, а процесс или связь умерли без решения пользователя. Сохраняется при перезапуске процесса. Сбрасывается следующим успешным подключением и ручным отключением (просмотр не сбрасывает). Сбрасывается и новым запросом на подключение (нажатие, загрузка, Always-on, перезапуск системой): туннель возвращается, поэтому «остановился неожиданно» не мигает перед CONNECTING и не стоит рядом с ошибкой следующей неудачной попытки. Потеря туннеля позже пишет его заново. Запуск от приёмника загрузки или обновления тоже запрос: приёмник пишет желание до создания службы, старт процесса читает его как смерть, и команда `BOOT` в движке подтверждает желание заново, снимая ложное «остановился неожиданно» до первой публикации. |
| `stopReason` | `String?` | Причина при `unexpectedStop`: код `ApplicationExitInfo` (`low_memory`, `crash`, `crash_native`, `anr`, `user_stopped`, `package_updated`, …), `process_died`, `tunnel_lost`. `user_requested` система пишет и для принудительной остановки, и для смахивания из «Недавних», и для чистильщика, и (до API 34) для обновления: интерфейс называет обоих возможных авторов («закрыли вы или сам телефон») и показывает совет про батарею. `user_stopped` (остановлен пользователь Android) получает общий текст. |
| `needsPermission` | `Boolean` | Нет согласия VPN (на Android 13+ без разрешения на уведомления это единственный видимый сигнал). Сохраняется; сбрасывается, когда согласие появилось или пользователь подключился. При `true` `state` тоже NEEDS_PERMISSION. |
| `lastFailure` | `String?` | Текст последней неудачи запуска (из ядра, на английском). Сохраняется между перезапусками; сбрасывается успешным подключением или новым запросом пользователя. |
| `failureKind` | `String?` | Код `lastFailure`: `no_server`, `core_start`, `apps_none`, `permission`, `connect_failed`, `restricted_start`, `tunnel_lost`, `protection_off`, `core_stop_timeout` (ядро не остановилось вовремя, процесс `:vpn` завершён и поднимется заново), `repeated_crash` (процесс падал подряд до первого CONNECTED, автоперезапуски прекращены). Текст интерфейс выбирает по коду. |
| `skippedPackages` | `List<String>` | Выбранные приложения, которых нет на телефоне; пропущены при построении туннеля. Пусто, пока туннель не строился. |
| `failureReason` | `String?` | `ErrorInfo.reason` ядра для неудавшегося подключения (например `no_server`), если оно его прислало. Вместе с `failureKind` определяет текст ошибки. |
| `warnings` | `List<String>` | `ConnectResponse.warnings` последнего успешного подключения; непусто только при CONNECTED. Принадлежат подключению, которое сделала служба: ядро не отдаёт их в статусе, а ответ `RestartProfile` получает только вызвавший. Поэтому после перезапуска, который ядро сделало само, они пусты (неизвестное показывается как «нет»). |
| `coreEpoch` | `Int` | Сколько раз ядро Go было оборвано снизу и будет запущено заново: изменение значит «возьми `endpoint()` заново». Интерфейс делает это сам: `AppEnv` передаёт эпоху в `CoreSession.onCoreEpoch`, клиент ядра сбрасывается, адрес, полученный до смены, не кешируется. |
| `tunnelSeq` | `Int` | Номер туннеля в процессе службы: растёт при каждом переходе ядра в CONNECTED (новое подключение, пересборка через `reconnect`, перезапуск ядра изнутри, возврат после падения), как бы коротка ни была пауза. Живёт в службе, переживает перезапуски интерфейса и начинается с 0 в новом процессе `:vpn`: сравнивать на изменение, а не на порядок. Интерфейс читает его в одном месте, `TunnelSight.after`: номер, сдвинувшийся при непрерывном CONNECTED, это пересборка, которую поток состояний скрыл; она считается новым туннелем (вердикт «проверено» не переносится) и новой сборкой. |
| `blackholeUntilMs` | `Long` | Время (epoch, мс), до которого трафик намеренно заблокирован на переходе; 0 — не блокируется. `trafficBlocked` = `blackholeUntilMs > 0`. |

Команды (AIDL `IVpnService`, новые методы только в конце списка):
- `connect(profileId)` (профиль `<= 0` — последний сервер). Состояние ERROR и причину сообщает статус. Вызовы `connect`, `reconnect` и `disconnect` из `VpnController` доходят до службы строго в порядке вызова (одна очередь `SerialCalls`).
- `reconnect(profileId)`: пересобрать туннель для того же или другого профиля без прямого трафика (удержание интерфейса до 30 с); о неудаче сообщает статус (ERROR, `failureKind`, `failureReason`). Идёт после ещё не законченного отключения, поэтому смену сервера нужно делать через него в любом состоянии, кроме IDLE, ERROR и NEEDS_PERMISSION (`SwitchPlan`). Внутри ядро сначала просят остановиться, переключение не пропускается.
- `disconnect()`.
- `setAutoConnectEnabled(enabled): Boolean`: пишет настройку и состояние приёмника загрузки вместе; `false`, если запись не дошла до хранилища или приёмник не удалось включить (настройка откатывается): переключатель должен показать прежнее значение. `VpnController.setAutoConnect` (suspend) возвращает это значение.
- `beginBusy(token, timeoutMs)` и `endBusy(token)`: пока идёт долгая операция в ядре (восстановление из резервной копии), процесс `:vpn` не останавливается и служба стоит в переднем плане, даже если интерфейс отвязался. Предел `timeoutMs` зажат до 15 минут, забытое удержание кончается само; службу будит один таймер на ближайший срок любого удержания. `beginBusy` возвращает `Boolean` (форма вызова прежняя, результат можно не читать): `true`, если удержание действует, `false`, если система не дала держать службу в переднем плане и удержание снято. Удержание защищает операцию в процессе `:vpn`, а не интерфейс, поэтому смерть интерфейса его не снимает: вызывающий должен задавать реальный `timeoutMs`. `VpnController.beginBusy` и `endBusy` (suspend). `VpnController.endBusy` снимает удержание на том Binder, который его принял, с пределом 3 с и без ожидания привязки (`HoldRegistry`): после ухода из приложения следующая привязка может быть через минуты. Незавершённый `beginBusy` отменить нельзя (он записывается, и `finally` вызывающего снимает его по метке). Срок удержания для восстановления из копии — 3 минуты: ядро не ограничивает операцию, а Argon2id плюс замена данных до 64 МиБ занимают секунды (десятки секунд на медленном 32-битном телефоне).
- Перезапуск ядра изнутри (`RestartProfile` по правке маршрутов или DNS) покрыт льготным периодом и удержанием интерфейса; `Reconnect.now` для настроек туннеля и приложений вызывает `reconnect(0)`.

### Уточнения после финального разбора (R7)

- **Перезагрузка, видимая только по аптайму.** Запись, которую сбросило обнаружение перезагрузки, сохраняется сразу, даже если изменение повторяет старые значения. Иначе следующий же вызов снова читал бы «перезагрузка» и стирал желание, записанное запросом на подключение при загрузке.
- **Отложенное завершение процесса.** Пока процесс ждёт конца busy-удержания после зависшей остановки ядра, новое подключение не запускает попытку (она зависла бы на замке ядра и показывала «подключение» до конца удержания): желание сохраняется, его продолжит следующий процесс, причина `core_stop_timeout` остаётся в статусе. `endpoint()` в это время сразу отвечает ошибкой, вызовы экранов к ядру не висят.
- **Команда, не дошедшая до службы.** Connect, Reconnect или Disconnect, потерянные из-за того, что служба не привязалась за 10 с или умерла, больше не пропадают молча: `VpnController.droppedCommands` → сообщение «Служба туннеля не ответила. Попробуйте ещё раз.». Пока интерфейс отвязан (человек ушёл), сообщение не показывается.
- **Закрытые баннеры.** Закрытие баннера «остановился неожиданно» или баннера сбоя забывается, когда причина закончилась: туннель поднят; туннель поднимается и статус уже не несёт эту жалобу (служба снимает её при любом запросе на подключение); пришёл сбой другого вида. Сбой, который показывается при CONNECTING («защита выключена»), закрытым остаётся. Закрытия переживают пересоздание экрана (`TunnelMemory`), но забываются после 30 с без экрана: за это время туннель мог подняться и умереть незаметно, а баннер у смерти процесса единственный сигнал.
- **Восстановление из копии и «Назад».** С момента, когда ядро начинает заменять данные, запрос и разбор его ответа не отменяются: выход из приложения кнопкой «Назад» (Activity уничтожается, область `AppEnv` отменяется) не обрывает замену на середине. Итог, пришедший без экрана, хранится в процессе (`RestoreNews`, только идентификатор строки) и показывается один раз при следующем открытии.
- **Предпросмотр ссылки.** `LinkClassifier.isSubscriptionPage` читает адрес как Go: пара запроса с битым `%` в значении отбрасывается, порт не из цифр делает адрес нечитаемым, порт отделяется по последнему двоеточию.

## Ожидающие изменения в интерфейсе

Ядро присылает признак «нужен перезапуск» (`needs_profile_restart`) только для части ключей (маршруты, DNS, `inbound.*`, `log.level`), а MTU, IPv6, FakeIP, исключения адресов, mux и проверка TLS читаются только при построении туннеля. Поэтому интерфейс сам ведёт состояние «сохранено, но ещё не в туннеле» (`RestartHub`, причины `PendingReason`: `Routing`, `Dns`, `Core` — достаточно перезапуска профиля ядра через `RestartProfile`; `Tunnel`, `Apps` — нужна пересборка туннеля через `reconnect(0)`). Состояние показывают баннер на экранах «Маршруты», «DNS» и «Подключение» и подпись «применится после перезапуска»; оно гаснет, когда туннеля нет или поднялся новый. «Переподключено» интерфейс пишет, только увидев, что туннель опустился и поднялся (`rebuildOutcome`). Тост «сохранено, применится после перезапуска» зависит от ответа ядра на само действие, а не от общего флага.

## Импорт и подписки

`ProfileService.ImportContent` для одной ссылки на подписку (http(s) с путём, либо зашифрованная ссылка, раскрывающаяся в неё) ничего не сохраняет: ответ `kind = SUBSCRIPTION_URL` без добавленных профилей. Интерфейс решает по `kind` ядра (предпросмотр `previewOnly`, локальный разбор только запасной): для подписки вызывает `CreateSubscription` и обновление (`SubscriptionIntake`, `SubscriptionsModel`), иначе ядро сохраняет разобранное. Ответ без `added_profile_ids` не называется успехом. Ядро не проверяет дубликаты при `CreateSubscription`: интерфейс сравнивает адрес сам и обновляет найденную подписку, а лишнюю группу, которую создало ядро для зашифрованной ссылки, удаляет (при неудаче группу ставят на «без автообновления»). Успех отката подписки ядро сообщает пустым ответом: ошибкой считается только поле `error`.

## Клиент API в Kotlin

HTTP/1.1 поверх `android.net.LocalSocket`: unary `application/json`, серверные потоки `application/connect+json` (конверт 5 байт, chunked). DTO генерируются из `proto/lavray.proto` скриптом `tools/protogen` в `@Serializable` классы (proto3 JSON: camelCase, int64 строкой, enum строкой). Ответ крупнее 32 МиБ (`MAX_UNARY_BYTES`) клиент не принимает: это `RESOURCE_EXHAUSTED` с причиной «слишком большой», клиент остаётся рабочим (на практике резервные копии малы).
