# Подпись APK LAVRay Android

Записка для владельца. Ключ в репозитории не хранится и не создаётся автоматически: `*.jks`, `*.keystore`, `*.p12` в `.gitignore`, а `scripts/ci-hygiene.sh` валит CI, если такой файл попал под git.

## Какой ключ что подписывает

| Сборка | Чем подписана | Где ключ |
|---|---|---|
| Локальная (`gradlew assembleDebug`, `assembleRelease` на ПК) | Отладочный ключ Android | `~/.android/debug.keystore`, AGP создаёт его сам; пароль `android`, алиас `androiddebugkey`; не секрет |
| `ci.yml` (push и pull request) | Отладочный ключ, свой на каждый запуск: раннер каждый раз новый | Секретов в этом процессе нет |
| `release.yml` (тег `v*`) | Релизный ключ владельца | Только секреты репозитория Actions, на диск попадает временным файлом на время сборки |

Как это устроено в `app/build.gradle.kts`: релизная подпись включается, когда заданы все четыре переменные окружения `LAVRAY_KEYSTORE_PATH`, `LAVRAY_KEYSTORE_PASSWORD`, `LAVRAY_KEY_ALIAS`, `LAVRAY_KEY_PASSWORD`. Если не задана хотя бы одна, Gradle молча подписывает отладочным ключом. Поэтому `release.yml` сам проверяет все четыре секрета первым шагом и падает с названием недостающего, а после сборки сверяет, что подпись не `CN=Android Debug`.

Следствия:
- APK из `ci.yml` (артефакты `apk-*`, суффикс `-ci`) годятся для проверки и не годятся для раздачи. Два таких APK из разных запусков нельзя поставить поверх друг друга, ключи разные.
- Публиковать можно только то, что собрал `release.yml`: имена `LAVRay-<версия>-<abi>.apk`, рядом `SHA256SUMS`.
- Локальный release-APK тоже подписан отладочным ключом: ставить его пользователям нельзя.

## Как выпустить релиз

1. Поднять `versionName` и `versionCode` в `app/build.gradle.kts`.
2. Написать `docs/release-notes/v<версия>.md`. Без этого файла (или с пустым) `release.yml` падает.
3. Закоммитить, поставить тег `v<версия>` ровно равный `versionName` и отправить тег. Релиз создаётся как `latest`.

## Как создать свой ключ

Нужны JDK и `keytool`. Ключ создаётся на вашей машине, в чужие руки и в репозиторий он не идёт.

```bash
keytool -genkeypair -v \
  -keystore lavray-release.jks -storetype PKCS12 \
  -alias lavray -keyalg RSA -keysize 4096 -sigalg SHA256withRSA \
  -validity 10950
```

`keytool` сам спросит пароль (вводится скрыто, в историю не попадает) и данные владельца. Не передавайте пароли ключами `-storepass` и `-keypass` в командной строке: они остаются в истории оболочки и в списке процессов.

- Для PKCS12 пароль ключа равен паролю хранилища: задайте один и тот же в обоих секретах (`LAVRAY_KEYSTORE_PASSWORD` и `LAVRAY_KEY_PASSWORD`).
- Срок 10950 дней (около 30 лет): сертификат не должен истечь, пока приложение живо.
- Сделайте минимум две копии файла `lavray-release.jks` и пароля (менеджер паролей и офлайн-носитель). Потеря ключа означает, что обновить установленные копии уже нельзя (см. ниже).
- Отпечаток для сверки (публичный, его можно хранить в README):
  `keytool -list -v -keystore lavray-release.jks -alias lavray` и строка `SHA256`.
- Текущий релизный ключ (создан 2026-11-10, с v0.9.3): `CN=LAVRay, O=LAVRay`, RSA 4096, PKCS12, псевдоним `lavray`, срок 10950 дней, SHA-256 сертификата `fe058a98b9abb7ba8c853c0ae39c893aeeffa6892eb5a243e22718c2ac58fbb3`. Файл хранится у владельца вне репозитория.

## Как положить ключ в четыре секрета

Секреты задаются в репозитории `anatolijlaptev1991-ctrl/lavray-android`: `gh secret set` не печатает значение и не принимает его в аргументах, если читать с stdin или из скрытого запроса.

Перед началом отключите запись истории на время сеанса:

```bash
# Git Bash / bash
set +o history
```
```powershell
# PowerShell
Set-PSReadLineOption -HistorySaveStyle SaveNothing
```

Хранилище (файл целиком, base64, через конвейер: значение нигде не набирается):

```bash
# bash
base64 -w0 lavray-release.jks | gh secret set LAVRAY_KEYSTORE_B64 --repo anatolijlaptev1991-ctrl/lavray-android
```
```powershell
# PowerShell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("lavray-release.jks")) | gh secret set LAVRAY_KEYSTORE_B64 --repo anatolijlaptev1991-ctrl/lavray-android
```

Остальные три, без `--body`: `gh` выдаст скрытый запрос и прочитает значение с клавиатуры.

```bash
gh secret set LAVRAY_KEYSTORE_PASSWORD --repo anatolijlaptev1991-ctrl/lavray-android
gh secret set LAVRAY_KEY_ALIAS         --repo anatolijlaptev1991-ctrl/lavray-android   # lavray
gh secret set LAVRAY_KEY_PASSWORD      --repo anatolijlaptev1991-ctrl/lavray-android
```

Проверка: `gh secret list --repo anatolijlaptev1991-ctrl/lavray-android` покажет четыре имени (значений он не показывает). Не пишите `echo пароль | gh secret set ...` и `--body пароль`: это попадает в историю. После этого удалите временные копии, кроме резервных, лежащих в безопасном месте.

Что делает `release.yml` с ключом: декодирует секрет во временный каталог вне рабочей копии (`$RUNNER_TEMP`, права 600), проверяет его через `keytool`, собирает, и удаляет каталог в шаге с `always()`. Значения нигде не печатаются, Actions маскирует их в журнале. Сборка идёт без кэша Gradle и без кэша конфигурации, чтобы подписанные результаты и секреты не попали в кэш. Если любой секрет пуст, релиз не собирается, отладочно подписанный APK не публикуется ни при каких условиях.

## Почему при смене ключа приложение приходится удалять

Android обновляет установленное приложение поверх только APK с тем же именем пакета (`io.github.anatolijlaptev1991_ctrl.lavray`) и тем же сертификатом подписи. Если сертификат другой, установка обновления отклоняется (`INSTALL_FAILED_UPDATE_INCOMPATIBLE`): система считает чужой подписью попытку подменить приложение. Так же ведут себя и отладочный, и релизный ключи: сборку с отладочным ключом нельзя обновить релизной и наоборот. Единственный выход без подготовки: удалить старую копию и поставить новую.

## Что при этом происходит с данными пользователя

Удаление стирает каталог данных приложения: профили и серверы, подписки, маршруты, DNS, настройки, статистику, журнал, выданное согласие на VPN и состояние автоподключения. Резервной копии системой нет: в манифесте `allowBackup="false"`, `dataExtractionRules` тоже ничего не переносят. Поэтому:
- Перед удалением пользователь делает экспорт на экране «Резервная копия» (файл через системный выбор файла) и импортирует его после установки.
- После переустановки нужно снова дать согласие на VPN и включить автоподключение.
- В заметках релиза, где ключ меняется, об этом пишется отдельной строкой в начале.

Лучшая политика: релизный ключ создаётся до первой публикации и не меняется.

## Смена ключа без удаления: схема подписи v3 (ротация)

APK Signature Scheme v3 (Android 9, API 28 и выше) позволяет поставить обновление с новым ключом, если APK несёт цепочку (lineage): старый сертификат, подписавший новый. Установленное приложение проверяет, что его текущий сертификат есть в цепочке, и принимает обновление.

Схема, `apksigner` из build-tools (проверьте на эмуляторе до выпуска, в CI это не автоматизировано):

```bash
# 1. цепочка: старый ключ подтверждает новый (нужны оба хранилища, делается один раз)
apksigner rotate --out lavray.lineage \
  --old-signer --ks old.jks --ks-key-alias lavray \
  --new-signer --ks new.jks --ks-key-alias lavray

# 2. подпись APK новым ключом вместе с цепочкой (после сборки без подписи или поверх неё)
apksigner sign --ks new.jks --ks-key-alias lavray --lineage lavray.lineage app-release.apk
apksigner verify --print-certs app-release.apk
```

Ограничения:
- Цепочку можно создать только пока есть старый ключ. Потерянный ключ значит, что остаётся только удаление.
- `minSdk` приложения 26: на Android 8.0 и 8.1 (API 26 и 27) v3 не читается, там обновление с новым ключом не пройдёт, нужна переустановка.
- Сборка в `release.yml` подписывает через Gradle одним ключом, цепочки там нет. Чтобы выпускать так, добавьте в процесс отдельный шаг `apksigner sign --lineage` (и файл цепочки в секреты).
- Переход с отладочного ключа на релизный технически та же процедура, но отладочный ключ у каждого свой и нестабилен, поэтому для пользователей его не берут за основу.

## Проверка подписи готового APK

```bash
apksigner verify --print-certs LAVRay-<версия>-arm64-v8a.apk
sha256sum -c SHA256SUMS
```

В списке сертификатов должен быть ваш отпечаток SHA-256 и не должно быть `CN=Android Debug`.
